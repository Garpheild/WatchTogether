# Совместная разработка

Команда — три разработчика, каждый работает со своим AI-агентом в OpenCode. Задача процесса —
дать агентам и людям непересекающиеся зоны, формальные контракты и предсказуемый порядок
интеграции.

## 1. Роли и зоны ответственности

| Роль | Основные задачи | Директории |
| --- | --- | --- |
| **№1 Frontend** | Страницы и компоненты, YouTube Player, REST-клиент, подключение WS на уровне UI, чат, участники, отображение состояния | `frontend/src/{app,pages,components,hooks,api,lib,styles,player}`, `frontend/index.html`, `package.json`, `vite.config.ts`, `tsconfig*.json`, `eslint.config.js` |
| **№2 Backend** | FastAPI, REST, PostgreSQL, SQLAlchemy, Alembic, модели и схемы, комнаты, вход, сообщения, инфраструктура | `backend/app/{api,core,rooms,participants,chat,use_cases}`, `backend/alembic/**`, `backend/pyproject.toml`, `backend/tests/{unit,integration}`, `infra/**`, `docker-compose.yml`, `.github/**` |
| **№3 Realtime** | ConnectionManager, WS-события, playback-сервис, синхронизация, чат-доставка, presence, reconnect, тесты realtime | `backend/app/websocket/**`, `backend/app/playback/**`, `backend/tests/realtime/**`, `backend/tests/unit/test_playback_math.py`, `frontend/src/realtime/**` |

Пересечения по зонам:

- `backend/tests/conftest.py` — общий, владелец №2, изменения согласуются с №3;
- `frontend/src/player/types.ts` (`PlayerAdapter`) — владелец №1; №3 потребляет интерфейс и
  согласует изменения;
- `frontend/src/api/types.ts` — владелец №1; изменения REST-контракта согласуются с №2;
- `docs/**` — общая зона (раздел 5);
- `AGENTS.md` в каждой зоне — владелец зоны, изменение через PR.

Никто не коммитит в чужую зону без явного согласования в PR/issue. Срочная правка «в чужом
файле» оформляется отдельным PR с указанием причины и ревьюером-владельцем.

## 2. Git workflow

- Основная ветка — `main`; прямые push'и запрещены (branch protection).
- Работа — в короткоживущих ветках от `main`, срок жизни ≤ 3 дней.
- Merge — только squash, после rebase на `main`; ветка удаляется.
- Один PR — одна логическая задача. Большие задачи делятся на вертикальные срезы.
- Ветки: `feat/frontend/<slug>`, `feat/backend/<slug>`, `feat/realtime/<slug>`,
  `docs/<slug>`, `fix/<zone>/<slug>`, `infra/<slug>`.
- Коммиты — Conventional Commits: `feat(realtime): add playback revision`, `fix(api): return 409 on room_full`,
  `docs(contract): specify chat dedup`, `chore(ci): split frontend and backend jobs`.
- Перед push: `git fetch origin && git rebase origin/main`.

### Порядок работы над задачей

1. Issue с описанием, acceptance criteria и ссылками на документы.
2. Ветка от свежего `main`.
3. Изменения только в своей зоне (или согласованный contract PR).
4. Локальные проверки из [DEVELOPMENT.md](./DEVELOPMENT.md#7-полный-чек-перед-pr).
5. PR по шаблону (раздел 4), ревью, squash merge.
6. Обновление [CHANGELOG_DEV.md](./CHANGELOG_DEV.md), если менялись контракты/архитектура.

## 3. Правила веток и конфликтов

- Часто подтягивать `main` (минимум раз в день), не держать ветку «в стороне» неделю.
- Не форматировать чужие файлы и не переименовывать общие символы «заодно».
- Конфликт в общем файле решает автор PR вместе с владельцем файла; при споре — обсуждение в PR,
  затем решение фиксируется в CHANGELOG_DEV.
- Миграции: только один открытый PR с миграцией одновременно. Если два PR создали ревизии —
  второй автор делает `alembic merge -m "merge heads"` после согласования с №2.
- Генерённые файлы (lock-файлы) конфликтуют редко; при конфликте пересобирать, а не мержить вручную.

## 4. Pull Requests

### Шаблон

```markdown
## Что сделано
Кратко, 2–4 пункта.

## Зачем
Ссылка на issue и раздел docs.

## Зона
- [ ] frontend
- [ ] backend
- [ ] realtime
- [ ] infra/docs

## Контракты
- [ ] REST не менялся
- [ ] WebSocket не менялся
- [ ] БД не менялась
- [ ] Контракт изменён: ссылка на docs + CHANGELOG_DEV

## Проверки
- [ ] lint
- [ ] typecheck / mypy
- [ ] тесты (какие)
- [ ] ручной сценарий (какой)

## Скриншоты / логи (для UI и realtime)
```

### Правила ревью

| Тип PR | Обязательные approvals |
| --- | --- |
| Обычный PR в одной зоне | 1 (желательно владелец смежной зоны) |
| Изменение REST API | 2: №2 + №1 |
| Изменение WebSocket-контракта | 2: №3 + №1 |
| Изменение схемы БД/миграции | 2: №2 + №3 |
| Изменение `PlayerAdapter`/`useRoomRealtime` | 2: №1 + №3 |
| Инфраструктура/CI | 1: №2 + любой второй |
| docs/ARCHITECTURE, docs/PROJECT_STRUCTURE | 1 любой второй |

- Автор не мержит PR, требующий двух approvals, без обоих.
- Ревьюер проверяет не только код, но и соответствие docs (имена полей, коды ошибок, права).
- PR без acceptance criteria или с «TODO вместо решения» не мержится.
- Ревью в течение рабочего дня; блокирующий комментарий помечается `blocking`.

## 5. Изменение общих контрактов

Контракты: REST API, WebSocket-события, схема БД, `PlayerAdapter`, `useRoomRealtime`.

**Процедура (contract-first):**

1. Создать issue с меткой `contract` и описанием: что меняется, зачем, кого затрагивает.
2. Открыть **docs PR**: правка `API.md` / `WEBSOCKET.md` / `DATABASE.md` + запись в
   `CHANGELOG_DEV.md`. Код в этом PR не меняется.
3. Получить approvals всех затронутых владельцев (см. таблицу выше). Merge docs PR.
4. Реализация — отдельными PR в своих зонах со ссылкой на docs-коммит.
5. Если реализация выявила проблему контракта — вернуться к шагу 2, не «договариваться в коде».

Правила совместимости:

- новые поля — только опциональные (клиент обязан игнорировать неизвестные поля);
- переименование/удаление поля — breaking change, требует синхронного PR во frontend и backend;
- новые события WS — добавляются в каталог и в `frontend/src/realtime/protocol.ts` в том же
  docs-цикле;
- изменение enum (`action`, `role`, `status`, `reason`) — breaking change;
- изменение имени поля в БД, но не в API, контрактом не считается, если DTO не меняется.

**Согласование API:** №2 пишет `docs/API.md` и Pydantic-схемы; №1 подтверждает, что клиент
сможет это потребить; №3 проверяет, что playback-поля совпадают с WS.
**Согласование WS:** №3 пишет `docs/WEBSOCKET.md`, типы `protocol.ts` и серверные схемы; №1
подтверждает удобство клиента; №2 проверяет, что сервисы и БД поддерживают событие.
**Согласование БД:** №2 пишет `docs/DATABASE.md` и миграцию; №3 проверяет `playback_states` и
поля presence; №1 проверяет, что DTO не ломают UI.

## 6. Порядок интеграции

Зависимости между работами:

```text
docs (контракты)
   ├── backend: схема БД → модели → миграции → REST → сервисы
   ├── realtime: protocol + managers → playback service → handlers → presence
   └── frontend: layout/UI → REST-клиент → player adapter → realtime hook → экраны комнаты
```

Рекомендуемые вехи:

| Веха | Содержание | Кто | Условие завершения |
| --- | --- | --- | --- |
| M0 | Docs + каркас проекта + docker compose + CI | все | `docker compose up -d db`, пустые приложения стартуют |
| M1 | БД + REST create/join/get/ws-ticket | №2 | интеграционные тесты REST зелёные |
| M2 | WS connect + snapshot + playback play/pause/seek | №3 | тест двух клиентов |
| M3 | Чат, presence, reconnect, смена видео, закрытие | №2/№3 | realtime-тесты зелёные |
| M4 | UI комнаты, чат, участники, обработка ошибок | №1 | ручной сценарий из TESTING.md |
| M5 | Совместная проверка, полировка, CI | все | критерии готовности MVP |

Правило: №1 не ждёт M2 целиком — UI и `PlayerAdapter` делаются по контрактам, realtime-хук
подключается, когда №3 отдаёт рабочий `useRoomRealtime`.

## 7. Взаимодействие AI-агентов

Каждый разработчик использует отдельного агента OpenCode. Чтобы агенты не мешали друг другу:

1. **AGENTS.md как граница.** Корневой `AGENTS.md` задаёт общие правила; `backend/AGENTS.md`,
   `frontend/AGENTS.md`, `backend/app/websocket/AGENTS.md` — правила зоны. Агент обязан прочитать
   свой AGENTS.md и ссылки на docs до изменений.
2. **Одна задача — одна ветка — один агент.** Не запускать двух агентов на одну ветку.
3. **Промпт содержит:** цель, acceptance criteria, список файлов/директорий, которые можно менять,
   ссылки на разделы docs, команды проверки. Без этого агент начнёт «улучшать» чужое.
4. **Агент не меняет контракты самостоятельно.** Если по задаче нужен новый endpoint/событие/поле,
   он обязан остановиться и предложить contract PR, а не придумывать имя.
5. **Агент не трогает чужую зону.** Исключение — явно перечисленные в задаче общие файлы.
6. **Ревью человеком обязательно.** Проверяются: соответствие docs, отсутствие дублей полей,
   тесты, отсутствие секретов в логах, отсутствие `TODO` вместо решения.
7. **Агент не устанавливает новые зависимости** без согласования: стек зафиксирован.
8. **Агент не переписывает чужие файлы «для консистентности»** и не делает mass-rename.
9. Перед PR агент запускает проверки и прикладывает их результат. «Тесты не запускал» — не
   принимается.
10. Спорные архитектурные вопросы выносятся в issue с меткой `architecture`; решение фиксируется
    в CHANGELOG_DEV.

Пример постановки для агента:

```text
Зона: backend (только app/chat и app/api/routes/messages.py).
Задача: GET /rooms/{room_code}/messages по docs/API.md §4.5.
Не менять: схемы БД, WS, frontend.
Проверки: pytest tests/integration/test_messages_api.py, ruff, mypy.
Если контракт неполон — остановиться и перечислить вопросы, не придумывать поля.
```

## 8. Коммуникация и ритм

- Ежедневный короткий sync (15 минут): что сделано, что блокирует, какие контракты затрагиваются.
- Все решения — в issue/PR, а не только в чате: история должна быть доступна агенту и человеку.
- Блокировка дольше 2 часов — сразу в общий канал, не «досиживать» в одиночку.
- Изменения docs — часть Definition of Done, а не отдельная «когда-нибудь» задача.

## 9. Definition of Ready / Done

**Ready (задачу можно брать):**

- есть issue с acceptance criteria;
- понятна зона и затронутые контракты;
- есть ссылки на docs;
- известны зависимости (чужая работа, миграция, endpoint).

**Done (PR можно мержить):**

- код в своей зоне, без несогласованных правок чужих файлов;
- тесты добавлены/обновлены и зелёные;
- lint/typecheck/mypy проходят;
- docs обновлены, если менялось поведение/контракт;
- CHANGELOG_DEV обновлён для архитектурных/контрактных изменений;
- нет `TODO` вместо решения и отладочных логов с токенами;
- получены нужные approvals;
- ручной сценарий проверен (для UI/realtime).

## 10. Известные задачи процесса

- Текущий `.github/workflows/ci.yml` рассчитан на корневой `package.json` и `yarn lint/typecheck/build`;
  после появления `frontend/package.json` и backend-зависимостей workflow переписывается на два
  job'а (`frontend`, `backend`). Это первый инфраструктурный PR №2.
- В корневом `README.md` описана старая структура (`infra/`, `models.py`, `schemas.py` в корне
  backend). README приводится в соответствие с `docs/` отдельным docs-PR.
- `CODEOWNERS` пока не создан; при включении branch protection рекомендуется добавить
  `.github/CODEOWNERS` с зонами из раздела 1.
