# Безопасность

Модель доступа простая: **ссылка на комнату + токен участника**. Регистрации нет, поэтому
безопасность строится на неугадываемом коде комнаты, криптостойких токенах, проверке роли на
сервере и жёсткой валидации входных данных.

## 1. Роли и разрешения

| Действие | Без токена | `member` | `owner` |
| --- | --- | --- | --- |
| Создать комнату | да | да | да |
| Войти в комнату по коду | да | — | — |
| `GET /rooms/{room_code}` | нет | да | да |
| Читать историю чата | нет | да | да |
| Получить WS-ticket | нет | да | да |
| Подключиться к WebSocket | нет | да | да |
| Play / pause / seek | нет | да | да |
| Отправить сообщение в чат | нет | да | да |
| Сменить видео | нет | нет | да |
| Закрыть комнату | нет | нет | да |
| Выйти из комнаты (`leave`) | нет | да | нет (`409 owner_must_close`) |

Правила:

- роль хранится только в `participants.role` и никогда не принимается из запроса;
- `join` всегда создаёт `member`; `owner` создаётся только в транзакции создания комнаты;
- частичный уникальный индекс `uq_participants_room_owner` гарантирует одного владельца на
  уровне БД;
- проверка владельца — на сервере, в сервисе/guard, а не только в UI.

## 2. Токены доступа участников

### Генерация

```text
raw_token = "wt_" + secrets.token_urlsafe(32)   # 256 бит энтропии
token_hash = sha256(raw_token.encode()).hexdigest()  # 64 hex-символа
```

- `raw_token` возвращается клиенту ровно один раз: в `201` ответах `create` и `join`;
- в БД попадает только `token_hash`; восстановить токен из БД нельзя;
- SHA-256 без соли и KDF достаточен, потому что токен — случайные 256 бит, а не пароль; перебор
  невозможен, а медленный KDF только увеличил бы задержку авторизации;
- сравнение — через поиск по уникальному индексу `uq_participants_token_hash`; timing-атака на
  индекс не даёт полезной информации при такой энтропии;
- токен не логируется, не попадает в URL, query, referrer и сообщения об ошибках.

### Хранение на клиенте

- `localStorage`, ключ `wt.access_token.{room_code}` — чтобы пережить перезагрузку страницы;
- `sessionStorage` не используется: потеря токена при новой вкладке ухудшает UX, а защита от XSS
  всё равно строится на CSP и отсутствии сторонних скриптов;
- при выходе из комнаты или закрытии комнаты токен удаляется;
- токен одного `room_code` не даёт доступа к другой комнате (проверка `participant.room_id`).

### Отзыв

- `leave` делает токен бесполезным для операций: `left_at` заполнен, auth возвращает `403`;
- закрытие комнаты запрещает все операции, кроме чтения состояния;
- отдельной ротации токенов в MVP нет. При компрометации — выход и повторный вход (новый
  участник) либо закрытие комнаты владельцем.

## 3. Авторизация REST

```http
Authorization: Bearer wt_...
```

Алгоритм `get_current_principal`:

1. извлечь токен из заголовка; нет заголовка → `401 invalid_token`;
2. `sha256(token)` → найти `participants` по `token_hash`;
3. не найден → `401 invalid_token`;
4. `left_at IS NOT NULL` → `403 forbidden`;
5. `participant.room.code != room_code` из пути → `403 forbidden`;
6. вернуть `Principal {participant, room}`.

Эндпоинты без авторизации: `POST /rooms`, `POST /rooms/{room_code}/join`, `GET /health`.
Для `owner`-действий дополнительно проверяется `principal.participant.role == "owner"`.

## 4. Авторизация WebSocket

Постоянный токен в URL не передаётся. Используется двухшаговый механизм:

1. `POST /api/v1/rooms/{room_code}/ws-ticket` с Bearer-токеном;
2. подключение к `/api/v1/ws/rooms/{room_code}?ticket=...`.

Ticket:

- JWT HS256, ключ `APP_SECRET_KEY` (≥ 32 байта, только из окружения);
- claims: `sub` (participant_id), `room`, `jti`, `iat`, `exp`;
- TTL 60 секунд;
- одноразовый: `jti` помещается в in-memory TTL-набор при успешном handshake; повторное
  использование → `403`;
- проверяется совпадение `room` с путём и наличие активного участника;
- `Origin` обязан входить в `CORS_ORIGINS` (защита от cross-site WebSocket hijacking);
- до `accept` любая ошибка → HTTP `403`; после `accept` — коды `4401/4403/4404/4409`.

Почему ticket в query, а не `access_token`:

- URL попадает в логи прокси и историю браузера; постоянный токен там недопустим;
- ticket живёт 60 секунд и одноразовый, поэтому его утечка через лог почти бесполезна;
- для доступа к логам нужен доступ к инфраструктуре, что выходит за модель MVP.

Альтернатива — передача ticket через `Sec-WebSocket-Protocol` — не выбрана: браузерный API
усложняет обработку, а выигрыш несущественен при одноразовом короткоживущем ticket. При
ужесточении требований доступен переход без изменения остальных контрактов.

## 5. Защита от подмены владельца

| Вектор | Защита |
| --- | --- |
| Передать `role = "owner"` в `join` | Поле отсутствует в схеме, `extra="forbid"` → `422` |
| Два владельца в комнате | `uq_participants_room_owner` |
| Сменить видео/закрыть комнату member'ом | Проверка роли в сервисе; UI-ограничение вторично |
| Выдать себя за владельца по имени | Имена уникальны в активной комнате (регистронезависимо), UI показывает бейдж роли |
| Использовать токен другой комнаты | Сверка `participant.room_id` с `room_code` пути |
| Подделать WS-ticket | Подпись HS256 + `exp` + `jti` + сверка `room` |
| Повторно использовать ticket | In-memory реестр `jti` на TTL |

## 6. Валидация входных данных

| Данные | Правила |
| --- | --- |
| `display_name` | trim; 1..32 символа; запрещены control-символы; регистронезависимая уникальность в комнате |
| `title` | trim; ≤ 80 символов; `null` допустим |
| `text` сообщения | trim; 1..500 символов; control-символы запрещены, кроме `\n` |
| `room_code` | `^[a-z0-9]{8,12}$`; генерируется сервером из алфавита без похожих символов |
| `video_url` | только поддерживаемые YouTube-хосты и пути; итоговый `video_id` — `^[A-Za-z0-9_-]{11}$` |
| `position_seconds` | число, finite, `0..86400` |
| `action` | enum `play/pause/seek` |
| `client_message_id` | UUID v4 |
| `limit` / `before_id` | int в допустимом диапазоне |
| Тело запроса | ≤ 16 КБ; неизвестные поля запрещены |
| WS-сообщение | ≤ 4 КБ; неизвестный `type` → `error` |

Дополнительно:

- SQL только через SQLAlchemy с параметризацией; конкатенация строк в запросы запрещена;
- ответы с пользовательским текстом рендерятся React'ом с экранированием; `dangerouslySetInnerHTML`
  запрещён;
- ссылки из чата не превращаются в кликабельные автоматически в MVP;
- ошибки не содержат stack trace, SQL и токенов.

## 7. Защита от злоупотреблений

| Действие | Лимит | Ключ |
| --- | --- | --- |
| Создание комнаты | 5/час | IP |
| `join` | 10/мин | IP |
| `GET /rooms/{room_code}` | 120/мин | участник |
| `GET .../messages` | 60/мин | участник |
| `POST .../ws-ticket` | 10/мин участник, 30/мин IP | участник + IP |
| REST в целом | 120/мин | IP |
| `chat.send` | 1/с, burst 5 | участник |
| `playback.command` | 5/с, burst 10 | участник |
| `sync.request` | 1/5 с | участник |
| `video.change` | 1/2 с | участник |
| WS-соединения | 3 на участника, 30 на комнату | участник / комната |

- Реализация — in-memory token bucket. При нескольких процессах лимиты станут per-process; в MVP
  процесс один.
- При `429` REST возвращает `Retry-After`; WebSocket — `error rate_limited`, при систематическом
  спаме — закрытие `4429`.
- IP берётся из входящего соединения. `X-Forwarded-For` учитывается только при
  `TRUST_PROXY_HEADERS=true` и доверенном reverse proxy; иначе заголовок подделывается и обходит
  лимиты.
- Код комнаты: 10 символов из алфавита 32 → ≈ 2^50 комбинаций. Перебор дополнительно ограничен
  лимитом `join` и `GET`.
- Комната на 10 участников не даёт разрастись одному злоумышленнику; владелец может закрыть
  комнату.

## 8. CORS, CSP и заголовки

**CORS** (backend):

- `allow_origins` строго из `CORS_ORIGINS` (`http://localhost:5173` в dev);
- `allow_credentials = false` (Bearer-токен, cookie не используются);
- `allow_methods = GET, POST, DELETE, OPTIONS`;
- `allow_headers = Authorization, Content-Type`.

**CSP** (frontend, отдаётся nginx):

```text
default-src 'self';
script-src 'self' https://www.youtube.com https://s.ytimg.com;
frame-src https://www.youtube.com https://www.youtube-nocookie.com;
img-src 'self' data: https://i.ytimg.com;
style-src 'self' 'unsafe-inline';
connect-src 'self' ws://localhost:8000 wss://watch-party.example;
base-uri 'none';
form-action 'self';
object-src 'none';
```

`'unsafe-inline'` для стилей нужен Tailwind/рантайму; скрипты inline не используются. Домен
`connect-src` подставляется под окружение.

Прочие заголовки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (страницу нельзя
встраивать), `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` с отключением
камеры/микрофона/геолокации. HSTS — при HTTPS-деплое.

## 9. Секреты и логирование

- `APP_SECRET_KEY` — только из окружения/секретов хостинга, не коммитится, ≥ 32 байт; используется
  для подписи WS-ticket.
- `DATABASE_URL` с паролем — только окружение.
- Ротация `APP_SECRET_KEY` инвалидирует только активные ticket'ы (≤ 60 с); access-токены не
  затрагиваются, так как хранятся хешами.
- В логи не попадают: `Authorization`, `access_token`, `ticket`, тексты сообщений (только
  `message_id` и `room_code`), тела запросов целиком.
- На reverse proxy отключается логирование query string для `/api/v1/ws/`: ticket одноразовый и
  живёт 60 секунд, но не должен попадать в access-логи без необходимости.
- Логи содержат `request_id`/`event_id`, `room_code`, `participant_id`, код ошибки — достаточно для
  разбора инцидента без персональных данных.
- Ошибки 500 логируются со stack trace на сервере, клиенту уходит `internal_error` без деталей.

## 10. Модель угроз (сокращённо)

| Угроза | Оценка | Мера |
| --- | --- | --- |
| Подбор кода комнаты | низкая | 2^50 вариантов + rate limit join |
| Кража ссылки | принято | Ссылка и есть приглашение; владелец может закрыть комнату |
| Кража токена через XSS | средняя | CSP, запрет сторонних скриптов, React-экранирование, нет `dangerouslySetInnerHTML` |
| CSWSH | средняя | Одноразовый ticket + проверка `Origin` |
| Подмена роли | высокая при ошибке | Роль только в БД, guard на сервере, constraint одного owner |
| Спам чатом/командами | средняя | Token bucket, лимиты на комнату |
| Огромные сообщения | низкая | 4 КБ WS, 16 КБ HTTP, 500 символов чат |
| Вредоносная ссылка | низкая | Whitelist YouTube-хостов, только `video_id` |
| SQL-инъекция | низкая | ORM/параметризация |
| Утечка через логи | средняя | Редакция токенов и ticket, отсутствие тел запросов |
| DDoS | вне MVP | Инфраструктурный уровень (прокси/хостинг) |

## 11. Осознанные ограничения MVP

- Нет пароля на комнату: любой, у кого есть ссылка, может войти (пока есть места).
- Нет модерации и бана участников; владелец может только закрыть комнату.
- Нет подтверждения личности: имя — отображаемое, не уникальный аккаунт.
- Rate limit и реестр ticket'ов живут в памяти одного процесса.
- Нет 2FA, email, восстановления доступа: потеря токена = повторный вход.
- Нет шифрования данных на уровне приложения; HTTPS/WSS обязательны на проде.

Эти ограничения соответствуют MVP и не должны «закрываться» наполовину реализованными механизмами
без отдельного решения команды.
