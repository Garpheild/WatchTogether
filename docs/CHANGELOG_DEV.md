# Журнал архитектурных решений и изменений документации

Файл фиксирует **почему** архитектура выглядит так, а не только что изменилось. Обновляется в том
же PR, где меняются контракты (`API.md`, `WEBSOCKET.md`, `DATABASE.md`) или архитектурные правила.

## Формат записи

```markdown
## [YYYY-MM-DD] — Короткое название

**Тип:** architecture | api | websocket | database | security | docs | process
**Автор:** имя / роль
**Затронуто:** список файлов и/или модулей
**Причина:** 1–2 предложения, какую проблему решаем
**Решение:** что именно выбрано
**Влияние:** frontend / backend / realtime / инфраструктура
**Действия:** миграции, обновление типов, breaking changes, задачи-продолжения
```

Правила:

- записи только добавляются, старые не редактируются (кроме опечаток);
- breaking change помечается `**Breaking:** да` и требует плана синхронного обновления;
- если решение отменяет предыдущее — новая запись ссылается на старую.

## [2026-11-24] — Создание архитектуры Watch Party

**Тип:** architecture
**Автор:** Senior Software Architect / Technical Lead
**Затронуто:** `docs/**` (11 документов), `AGENTS.md`, `backend/AGENTS.md`,
`frontend/AGENTS.md`, `backend/app/websocket/AGENTS.md`
**Причина:** нужна согласованная архитектура и контракты для параллельной разработки тремя
участниками; реализация ещё не начата.
**Решение:**

- выбран модульный монолит с модулями `rooms`, `participants`, `chat`, `playback`,
  `websocket`, `api`, `use_cases`, `core`;
- backend — Single Source of Truth для playback; состояние хранится якорем
  (`position_seconds` + `updated_at` + `revision`), актуальная позиция вычисляется клиентом;
- периодический broadcast отменён: события только по команде, запросу и при входе; дрейф лечится
  клиентским watchdog'ом;
- REST отвечает за жизненный цикл (создание, вход, история, ticket, выход, закрытие), WebSocket —
  за live-операции (playback, чат, presence, смена видео);
- доступ без аккаунтов: access-токен участника (sha256-хеш в БД), роль `owner` — поле участника,
  WS-авторизация через одноразовый JWT-ticket на 60 секунд;
- PostgreSQL хранит `rooms`, `participants`, `playback_states`, `messages`; presence, соединения,
  rate limit и реестр ticket'ов — в памяти одного процесса (`--workers 1`);
- playback вынесен в отдельную таблицу `playback_states` (1:1), чтобы модули не делили колонки;
- зафиксированы зоны ответственности трёх разработчиков и процесс contract-first PR.

**Влияние:** frontend, backend, realtime, инфраструктура
**Действия:**

- реализация начинается с вехи M0 (каркас, compose, CI) по
  [TEAM_WORKFLOW.md](./TEAM_WORKFLOW.md#6-порядок-интеграции);
- первый инфраструктурный PR: переписать `.github/workflows/ci.yml` под `frontend/` и `backend/`;
- привести корневой `README.md` и `.env.example` (`VITE_API_URL` → порт 8000) в соответствие с docs;
- при отклонении от контракта — сначала PR в docs, затем код.

**Breaking:** нет (первая версия).
